<tasks>

<task type="auto" id="1">
  <name>Task 1: get-secret helper</name>
  <action>
New `dot_local/bin/executable_get-secret NAME`. Dispatch: darwin -> `security find-generic-password -s NAME -w`; linux with `$DBUS_SESSION_BUS_ADDRESS` and `secret-tool` -> `secret-tool lookup service NAME` (KDE: KWallet/ksecretd exposes org.freedesktop.secrets, needs pam_kwallet auto-unlock); headless linux -> `pass show NAME` if `pass` exists, else `~/.config/secrets/NAME` (mode 0600, systemd-creds noted as upgrade). Add `libsecret` and `pass` to Pacfile; `pass` to Brewfile.
  </action>
  <verify>`get-secret` returns a test value on macOS; documented per platform in docs/</verify>
</task>

<task type="auto" id="2">
  <name>Task 2: Keys via env, fetched lazily</name>
  <action>
- Configs reference env only: opencode.json `options.apiKey` -> `{env:GEMINI_API_KEY}`; tmuxai `${GEMINI_API_KEY}`.
- LiteLLM: the four `gemini-*-direct` models are referenced nowhere else in the repo; delete them (and the `gemini_api_key` block) instead of porting. If you want them back later, use `os.environ/GEMINI_API_KEY`.
- No export at shell startup (keeps the Phase 11 budget). Instead add thin zshrc wrappers: `opencode() { GEMINI_API_KEY=$(get-secret gemini-api-key) command opencode "$@"; }` and the same for `tmuxai`. Key exists only in that process environment.
- Remove `gemini_api_key` from the `.chezmoi.toml.tmpl` prompts and all templates; add a one-time `get-secret --set gemini-api-key` instruction to docs. Rotate the exposed key (it sat in 644 files).
  </action>
  <verify>`grep -rE "AIza" ~/.config/opencode ~/.config/litellm ~/.config/tmuxai` empty after apply; `opencode` and `tmuxai` still authenticate</verify>
</task>
